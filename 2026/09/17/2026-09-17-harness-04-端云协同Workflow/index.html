04｜端云协同 Workflow：本地认领、Git 交付与云端继续执行

核对日期：2026-09-17。代码根目录：E:\MoreProject\learn_foresign_engine。本文解释当前工作区实现，不执行本地 Git 提交、远端推送或真实云端工作流。

所有源码为关键路径节选，每行附原行号及教学解释；未展示的上下文会明确说明。注释只存在本文，没有修改项目源文件。

1. 先把三个容易讲错的概念纠正

1.1 executionLocation 不是一个万能调度开关

原来的概括是“节点标 local，云端自动下发到 IDE”。当前源码更具体：

  • 引擎创建 human_first 节点执行时，可先停在 waiting_human_input，不立即启动 Agent。
  • 初始 NodeExecution 的 executionLocation 可仍为 cloud。
  • 本地工具经 MCP 业务入口发现候选、主动 start-local 认领，服务端才写入 local + local_plugin。
  • 因而不是所有 waiting_human_input 都等于本地任务，也不能说定义里填 local 就保证平台推送并启动本地进程。

代码：packages/backend/src/workflow/workflow-engine.service.ts:1244-1258、:1410；本地认领：packages/backend/src/twork-agent-mcp/twork-node-execution.service.ts:212。

1.2 Git SHA 校验不是数字签名验签

更准确的术语是：服务端校验提交存在性、祖先关系和实例分支可达性。

这里没有看到使用公钥验证 GPG/SSH commit signature 的流程。SHA 用于标识 Git 对象与关系，不证明提交者身份、代码安全、测试通过，也不能泛称“防止所有历史被改写”。

身份授权由 PAT、scope、实例权限、节点执行人等机制负责；Git 图校验负责证明“这份交付建立在指定基线之上，且已进入实例远端分支”。

1.3 随机 lease token 不等于单调 fencing token

  • leaseToken：随机秘密凭证，服务端存哈希；证明持有某次租约凭证。
  • stateVersion：递增版本，用于 CAS 抢占，防止两个请求基于同一旧状态都成功。
  • executionOwnerId：业务执行用户。
  • clientSessionId：本地调用会话身份。

严格分布式 fencing 通常要求下游资源比较递增代次并拒绝陈旧操作。这里只能按具体路径描述凭证校验和 CAS，不能把随机 token 本身称为全系统严格 fence。

2. 为什么会需要端云协同

以“分析需求 → 修改本机仓库 → 云端后续评审”为例：

  • 云端适合统一上下文、流程状态和自动节点执行。
  • 本地 IDE 可能已具备开发环境、用户手头未提交的修改、需要人参与的工具。
  • 不能为了跑一个节点把整条 Workflow 都迁移到本机。
  • 因而将节点执行权交给本地，保留工作流推进权和完成判定在云端。

这不替代 CI：Git 提交已回传不代表测试一定通过。CI 可以作为后续质量门禁，或由具体工作流节点执行，但不是 SHA 本身能保证的事情。

3. 先看全链路

步骤 调用方/服务 关键产物
1 WorkflowEngine.triggerNode waiting_human_input 等待中的节点执行
2 本地 MCP 工具查询 可读节点上下文、可执行候选、busy 状态
3 start-local PAT/权限校验、CAS 认领、startHeadSha、lease
4 本地 IDE/用户 按基线修改、测试、commit、非强制 push
5 complete-local baseSha、commitSha、summary、幂等键
6 GitCollaborationService fetch 远端、存在性/祖先关系校验
7 服务端 worktree 同步 确认干净、复核远端、快进

本地执行者是主动调用工具领取，不是云端可以随意遥控一台 IDE 执行命令。 MCP 提供工具发现、参数和调用语义；业务租约、Git 校验和状态机仍是平台自己实现的。

5. 节点发现：可读不等于可执行

getMcpRunnableAgents 区分：

  • currentNodes：展示实例执行进度。
  • availableAgents：当前调用用户实际可认领/执行的候选。
  • busyAgents：已有云端执行、本地活跃 lease 等占用。

发现接口能看到节点，不代表有权修改它。节点执行人、实例归属、当前占用、云端 run/session 状态都影响是否可执行。

上下文聚合还会向上遍历已完成的传递祖先，而不只是取直接上游：这样本地执行者可以看到需求、设计等前置节点产物，而不是孤立拿到一句节点名。对应 twork-agent-discovery.service.ts:422-510。

5.1 租约过期的“展示恢复”

当本地 running 租约过期，候选查询可将它对外回显为 localExecutionPreviousStatus，重新让调用者看到可认领状态。这不是后台定时器已经把数据库 status 改回去了。

新 start-local 接受 expiredLocalClaim 时，才进行实际重新认领。展示状态、数据库原始状态和执行权限是不同层，不能合称“15 分钟自动恢复一切”。

6. 本地认领：先拿执行权，再碰 Git

startLocalExecution 先执行节点写授权和业务检查：

  1. 调用者身份和实例/节点权限合法。
  2. 实例启用 git_enabled，并存在 instanceBranch 和 authoritativeHeadSha。
  3. 可选 expectedHeadSha 必须与权威 HEAD 一致。
  4. 检查幂等键、同一 clientSession、当前状态是否允许领取。
  5. 不与活跃本地租约、云端 Agent run、云端 Session 冲突。
  6. 最后用 stateVersion + status + 无活跃 Session 条件做 CAS。

为什么检查两遍？前面的查询提供可理解的业务错误，但查询后可能发生竞争；CAS 才是在写入时再次确认观察到的状态没有被改变。

6.1 源码逐行注释：保存恢复状态与生成 lease

来源：packages/backend/src/twork-agent-mcp/twork-node-execution.service.ts:205-211。

同会话重试会经过新 token 生成和更新，不能说“明文 token 永远只返回一次且重试总是同一个”。幂等业务效果与返回凭证轮换需要分开理解。

6.2 源码逐行注释：CAS 条件与状态写入

来源：同文件 :212-246。

两个人同时读到 version=7，第一人将其更新为 8；第二人的 where version=7 不再命中。这是乐观锁，而不是持有数据库事务 15 分钟。

返回结果包括 instanceBranch、repository 信息、startHeadSha、leaseToken、leaseExpiresAt。先拿到成功认领结果再开始本地工作，避免已经改代码才发现节点被别人占用。

7. 当前代码有两类收尾路径，不能混讲

这是本次核对的重要结论。

路径 输入特征 核心行为
start-local → complete-local baseSha、commitSha、summary、idempotencyKey 本地提交并推送，服务端验证远端 Git 交付
prepare/reportProgress/finalize 服务方法 leaseToken、clientSessionId、startHeadSha 等 verifyLease 后进入另一套进度/收尾逻辑

TworkNodeExecutionService.verifyLease 检查 owner、clientSessionId、token hash、过期时间。但 controller 的 complete-local 调用的不是这个方法。

7.1 源码逐行注释：complete-local 实际下发了什么

来源：packages/backend/src/twork-agent-mcp/twork-agent-mcp.controller.ts:1314-1320。这是 respond 包装器内的回调片段。

因此不能声称 complete-local 具有与 verifyLease 完全相同的过期/token 检查。它有 PAT/scope、实例权限、执行人、当前 claim、baseSha 和 Git 验证等检查，但保障层次不同。

8. 完成请求的幂等，不只是一个 requestId

同一节点和幂等键命中已有完成记录时：

  • 指纹不同：同一个键被用于不同请求，冲突。
  • 相同请求已经 completed 且有 resultSnapshot：返回保存结果，不重复完整收尾。
  • processing：可以在一定条件下续接被中断的收尾。

8.1 源码逐行注释：同键不同内容与完成回放

这处理的是“服务端成功了，客户端却没收到响应”的常见故障。它不意味着数据库、Git fetch/merge、状态更新和下游调度处于同一个原子事务。

9. Git 交付校验：三个 SHA、两个祖先关系

先定义：

名字 来源 含义
startHeadSha start-local 时服务端权威 HEAD 本次工作开始的基线
baseSha complete-local 请求 必须与上述基线一致
commitSha 本地交付 此次希望确认的提交
remoteHeadSha 服务端 fetch 后读取 实例分支现在的远端头

成功的有变更交付应满足：baseSha 是 commitSha 的祖先，commitSha 是 remoteHeadSha 的祖先。祖先关系允许相等，具体无变更情况有单独处理。

commitSha 不必永远等于 remoteHeadSha。 远端可以已包含其后的提交，只要交付仍在实例分支历史上；后续服务端同步还会复核远端状态。

9.1 为什么服务端自己 fetch

不能相信客户端一句“我已经 push 了”。服务端使用自己的授权上下文，从实例绑定的仓库/分支拉取，并在沙箱 Git 环境检查对象。

位置：packages/backend/src/workflow/workflow-git-collaboration.service.ts:428-442。这里更新的是远端跟踪引用；源码 fetch refspec 的 + 不能误读为本地插件可以 force push 远端。fetch 与 push 方向不同。

9.2 源码逐行注释：对象存在与双祖先校验

来源：同文件 :464-483。前面已验证 base commit 存在，并处理无变更分支。

底层使用 git merge-base --is-ancestor。这证明可达性，不验证提交内容符合需求，也不验证作者签名。

9.3 源码逐行注释：没有改代码也可以完成

来源：同文件 :450-462。

有变更时还会计算 name-status/numstat，形成 changedFiles 与 diffStat。摘要可以由本地提供，文件差异由服务端从 Git 计算，二者信任等级不同。

10. 为什么验证通过还要同步 worktree

验证成功只说明“远端 Git 图中有这份交付”，不说明云端后续节点的工作目录已经在正确版本。

syncInstanceWorktreeToRemoteHead（同文件 :513）会检查：

  1. 服务端 worktree 是否干净，避免覆盖已有未提交修改。
  2. 远端 HEAD 是否仍等于刚验证的 expectedRemoteHeadSha。
  3. 用 fast-forward 路径同步，不能默默制造额外合并或覆盖本地分叉。

这一步失败不能直接推进下游，否则下游读的文件可能不是刚认可的交付。

实例级 Git 锁的边界要谨慎：源码另有 workflowInstanceGitLock 管理某些 finalize 路径；不要因此推断 complete-local 的 fetch→验证→同步→DB 收口整体都被同一个锁原子覆盖。需要逐个调用路径确认。

11. 引擎收口：何时后继节点才开始

completeExternalNodeExecution 在写入前再次查询当前状态，检查 running、owner、来源、location 与 startHeadSha，然后写入交付信息、清理认领字段、更新权威 HEAD、完成节点，最后 onNodeCompleted。

11.1 源码逐行注释：更新实例权威头并推进

来源：packages/backend/src/workflow/workflow-engine.service.ts:3765-3782。

源码写前复查是防御措施，但不是单条带所有版本条件的 CAS，也不能从多个 await 推导出整个流程原子性。应分清“重复完成可以续接/回放”与“不会出现任意中间状态”。

12. 四层授权与两类凭证

12.1 授权分层

  1. 身份：Bearer PAT 验证，得到 employeeId、tenantId、scopes 等可信 principal。
  2. 功能权限：workflow:read、workflow:execute、workflow:stop 等 scope。
  3. 资源权限：实例、Desktop、定义、项目的归属和访问关系。
  4. 节点执行权限：assignedExecutorId、executionOwnerId、当前运行状态和相互占用。

可参考：twork-mcp-auth.guard.ts:13、node-executor-authorization.service.ts:12、twork-agent-identity.service.ts:136，均位于 packages/backend/src/twork-agent-mcp/。

12.2 PAT 与 leaseToken 的区别

凭证 表示什么 生命周期
PAT 谁在调用、有哪些授权 scope 用户/工具访问凭证生命周期
leaseToken 某次认领的临时凭证，适用于实际校验它的接口 当前认领的租约周期

拥有 PAT 不代表可以写所有节点；拥有旧 lease 也不应被理解为无限期执行权。具体强制检查必须逐路由确认，尤其 complete-local 与 finalize 的差异。

13. 异常场景与正确表述

场景 当前机制 不要错误承诺
两个客户端同时认领 stateVersion/status CAS，失败返回冲突 不是全工作流全局排他锁
云端已运行 检查活跃 run/session，拒绝本地占用 查询检查不天然包含所有未来并发变化
本地掉线 租约到期后候选回显可恢复，新会话可重领 到期不等于自动终止本机进程或回滚已 push 内容
本地运行超过 15 分钟 按接口支持的续租/重新认领语义维护资格 reportProgress 当前不能假定自动续期
同键完成请求重试 指纹检查、resultSnapshot 回放 不同内容不能复用同键
commit 尚未到服务端 commit_not_found 等明确失败 不以客户端字符串为完成证明
基线关系不成立 祖先校验失败 不是密码学签名验证
远端变化/worktree 脏 同步阶段拒绝或要求解决冲突 不自动 force 覆盖用户数据
Git 完成后 DB/响应中断 processing 记录与续接逻辑 不能说 Git 与 DB 共同事务已提交

特别注意：本地断联不等于没有副作用。执行者可能已 commit/push，或输出摘要已写入；只是节点 completed 和下游推进还有服务端门禁。

14. 设计权衡：为什么这样做，而不是另一个方案

MCP 与消息队列不是互斥选项

MCP 面向本地 AI 工具，提供可发现的业务动作和结构化参数；队列偏向任务投递和消费可靠性。可以使用 MCP 暴露领取/回传接口，同时在后端使用持久队列调度。

不能说“队列不能人工确认”——它可以与审批系统结合；只是不能直接替代 MCP 的工具语义、用户上下文和本项目的权限检查。

为什么 lease 放数据库

节点状态、stateVersion、owner、lease 和幂等标识都与业务实体关联，放在同一持久化体系便于条件更新与审计。代价是要自己管理过期语义、查询回显和竞争；不是有 Redis TTL 才叫 lease。

为什么用 Git 提交，而不是上传一个文件清单

Git 提交能表示内容快照与父子关系，远端分支是双方共享的交付位置；服务端可以验证交付是否可达，并计算真实差异。文件清单只能描述“声称改了什么”，很难单独表达完整版本基线。

但 SHA 不证明测试结果；如果工作流需要质量保证，应另加可验证测试报告、CI 结果或评审节点。

15. 面试表达模板

一分钟版

我们把工作流推进留在云端，但允许本地 AI 工具认领节点执行。引擎产生等待中的节点后，本地经 MCP 获取上下文并申请执行权，服务端校验用户、实例和节点权限，用版本 CAS 避免与其他本地或云端执行冲突，同时返回实例分支和起始 HEAD。本地完成修改、测试、提交和推送后回传 baseSha、commitSha 与摘要；云端自己 fetch，校验基线祖先关系及提交在实例分支上的可达性，再同步工作区、完成节点并推进下游。Git 校验不是数字签名，租约和幂等也各有边界，不能宣传端到端 exactly-once。

追问：人一直不回来怎么办？

租约到期后可发现并重新认领，节点不应永久被某个客户端占住。但这不自动取消本地进程或撤销已经推送的 Git 状态，接管仍需要重新核对权威基线。

追问：为什么一定要 startHeadSha？

否则本地可能基于旧版本工作，服务端仅看“有一个 commit”无法判断是否延续正确实例基线。服务端认领时保存起点，完成时比对 baseSha，并验证提交 ancestry。

追问：防历史改写能保证多强？

当前检查确保基线是交付祖先、交付可达于远端分支；不证明全部仓库历史从未发生任何变更，不验证提交签名，也不证明提交语义正确。应准确说是基线连续性和分支归属校验。

追问：哪些地方还需要改进？

作为改进建议而非已实现功能：统一 complete-local 与 token/lease 代次校验语义，明确整段 Git 收口的并发边界，补全长耗时本地执行的续租契约，围绕中间状态建立故障恢复测试。不要把现有随机 token 直接宣传为所有下游都会执行的严格 fencing。
