03｜沙箱内 Agent Runtime：从接收任务到工具执行、断线回放与升级

核对日期：2026-09-17。仓库：E:\MoreProject\learn_foresign_engine。依据当前工作区源码，不代表线上实际部署配置。

本文摘录关键执行路径，不是把 5000 多行服务文件全部复制。标为“源码逐行注释”的代码保留原语句，每行末尾的 // L原行号：解释 为教学注释；片段之间有省略，不能拼起来当完整程序运行。项目源码未被修改。

1. 先理解：到底是谁在做什么

你可以用“请修改工作区里的一个函数并运行测试”贯穿理解：

  1. Backend 确定是谁发起、在哪个工作区、使用哪个模型、允许写哪里。
  2. Backend 将这些配置发给沙箱里常驻的 agent-service.mjs。
  3. agent-service 调用 Claude Agent SDK 的 query。
  4. 模型产生工具调用意图，SDK 驱动工具执行；读文件、改文件、运行测试发生在沙箱内。
  5. SDK 返回一串消息，服务将它们翻译成平台事件，通过 SSE 交给 Backend。
  6. Backend 再负责持久化、计费、广播；浏览器并不直接连这个 Node 服务。

不是 Backend 每收到一个 tool_use，就再调用一次远端 Bash。 沙箱内 SDK 已经负责工具执行循环，Backend 消费的是执行过程和结果。

1.1 三种 Session，绝对不能混用

标识 所在层 含义 生命周期
Backend sessionId 平台数据库 用户的一段聊天 可包含多轮执行
sandbox sessionId agent-service 内存 Map 一次 Runtime 执行及其 SSE 通道 进程内、终态有限保留
sdkSessionId SDK 历史机制 用于 SDK resume 的对话身份 与 SDK 历史文件及路径相关

options.resume 用的是第三种，不是平台 sessionId；SSE 重连用的是第二种，不需要重新 query。

3. 为什么先创建会话，再订阅，最后才执行

执行时序：Backend POST /sessions → 得到 created 会话 → GET /sessions/:id/events → attachClient → start → execute → query。

这解决的是“有副作用的任务已经开始，但接收方还没建立通道”的窗口。创建后 30 秒没有人订阅，会话会被取消并清理，防止留下无主执行。对应 agent-service.mjs:3172。

关键问答：断线为什么不重新发送 prompt？

因为模型可能已经执行了写文件、提交代码或调用外部服务。重发 prompt 是再次执行任务，可能重复副作用；重连同一个 session 的事件流只是补齐观察结果，两者不是同一种重试。

4. query 并不是一次普通聊天 API

query 的输入不仅有 prompt，还有 cwd、模型、systemPrompt、MCP、权限回调、AbortController、resume 等执行上下文。它返回一个异步可迭代消息流，不是单个字符串。

配置构造见 agent-service.mjs:3794：

  • cwd：工具工作的起始目录。
  • includePartialMessages: true：需要增量消息供平台流式展示。
  • persistSession: true：启用 SDK 历史持久化；不等于持久化 HTTP Session Map。
  • mcpServers：接入平台下发的工具服务器。
  • env：默认给 SDK 的是代理 token 和 Backend Proxy 地址，而非真实长期模型 Key。
  • canUseTool 与 PreToolUse：执行前检查或进入人工交互。

4.2 SDK 消息如何变为平台事件

源码 agent-service.mjs:4103 起按 message.type 分派：

SDK 内容 平台处理
system/init 捕获 SDK session_id，发 __SESSION_ID__
assistant/stream_event 转换 text、thinking、tool_use、tool_input_delta 等
user/tool_result 工具执行结果与步骤状态
人工问答、审批 user_question / permission_request
最终汇总 __FINAL__，携带响应、usage、cost、turns、SDK 身份等

Backend 收到 SSE socket close 不能当作执行成功；必须区分 FINAL 到达与网络中断。

5. SSE + ACK：可靠到哪一层

5.1 先记住这个例子

沙箱发出 1、2、3、4，Backend 连续收到 1、2 后断线。重连请求携带 Last-Event-ID=2，沙箱回放 3、4，再继续推送新事件。

如果 Backend 收到 4，却没有收到 3，不能直接把游标升到 4，否则累计 ACK 会把 3 当作已确认丢弃。Backend 因而维护的是最高连续事件号，不是“见过的最大数字”。

5.4 不能承诺 exactly-once

Backend 接收端见 sandbox-agent-sse.service.ts:589-663：完整帧 → JSON 解析 → ID 检查 → 连续性检查 → 同步交接事件 → 推进游标。

这里的 ACK 不是数据库事务提交确认，也不是浏览器已收到确认。下游还可能异步处理，因此 Backend 在交接后崩溃存在不同层状态不一致的窗口。

还有这些限制：

  • 默认每 2 秒 ACK，FINAL 到达时尽快 flush。
  • 默认终态保留 120 秒，FINAL 已 ACK 且缓存空可提前回收。
  • 单条 SSE 连接发生背压时会被关闭，依靠重连恢复。
  • 未 ACK 的 replay buffer 没有事件数/字节数硬上限，长期未确认会占内存。
  • 进程重启、容器销毁或保留期结束后，不保证回放。
  • 浏览器还有另一套 Redis Stream + seq 恢复协议，见第一份文档，不能混用两种游标。

7. Write Policy：不要把提示词当权限系统

7.1 三层职责

  1. Backend resolver 从 Session、Desktop、Workflow 和成员权限解析可信 writeRoot、protectedPaths 等。浏览器 requestedWorkingDir 不是最终权威。
  2. WriteGuard 在 PreToolUse/canUseTool 检查已知原生工具的路径及可识别命令写目标。
  3. SDK filesystem sandbox 尝试用系统侧文件系统约束进一步限定执行。

配置来源：packages/backend/src/session-write-policy/session-write-policy.resolver.ts:41；接入位置：agent-service.mjs:3930、:4014。

7.3 面试必须区分“设计意图”和“当前保障”

  • writePolicy 的 shadowMode 默认开启；普通越界可记录“本应拒绝”而不阻断，成员保护路径另有强制规则。
  • 未提供 writePolicy、无法确定命令写影响等路径存在审计后放行。
  • 任意 MCP 的副作用不自动被原生文件工具 guard 全覆盖。
  • policyFingerprint 是配置一致性诊断用的哈希，不是授权数字签名。
  • 容器是执行环境边界，不等于同容器内每个 Session 都有独立安全域。
  • 这些是治理边界和加固方向，不应作为“百分之百隔离”的简历宣传。

8. 热更新：更准确地叫“运行服务文件更新 + 受控重启”

流程见 sandbox-agent-updater.service.ts:396 起：

  1. Backend 读取本地 Runtime 版本，调用沙箱 /health。
  2. 对比版本及 write guard capability。
  3. 需要更新则部署依赖文件，再部署主服务文件。
  4. 活跃会话存在时先暂存，不立即重启。
  5. 确认受 wrapper 监管后调用 /reload；服务再次检查活跃会话。
  6. 服务退出 42，wrapper 拉起新 Node 进程。
  7. Backend 再次检查版本和能力。

非腾讯路径使用临时文件与 mv 逐文件替换，腾讯 Files API 路径不具有同样的逐文件原子替换步骤。两者都不能描述为多文件原子事务；源码未见自动回滚旧 Runtime 的完整机制。

9. 面试讲法：从 60 秒到深挖

60 秒版

我们把平台业务控制面与 Agent 工具执行面拆开。NestJS 管用户身份、会话、模型配置与事件持久化；沙箱里常驻 Node Runtime，直接嵌入 Claude Agent SDK，让文件和命令操作就近执行。任务创建后先建立 SSE 再启动 SDK，运行事件带连续序号，通过 ACK 和内存回放恢复短时断线。写路径采用工具 guard 和 SDK filesystem sandbox 分层治理，但会区分审计模式与强制模式。服务升级通过版本检测、暂存文件和 wrapper 受控重启，不是在线无缝替换。

追问 1：为什么不用 Backend 直接执行 SDK？

因为用户命令、依赖安装和工作区 I/O 应尽量在租户执行环境内完成，避免把 Backend 变成用户代码宿主。代价是要处理跨进程事件、控制请求、凭证和生命周期。项目正常路径如此，但仍保留 Backend SDK fallback，不能说所有路径都被硬隔离。

追问 2：为什么既有容器，又有写策略？

容器限制执行环境与宿主/其他环境的关系；写策略限制同一个工作区内不同任务能改哪些路径。它们保护的对象不同，不能互相替代。

追问 3：SSE 断线后如何避免重复执行？

恢复同一 sandbox session 的事件流，而不是重新调用 query。事件 ID 去重解决重复展示；不代表外部副作用具有全局 exactly-once。

追问 4：ACK 后进程崩溃是否会丢事件？

可能。ACK 的层级是 Backend 接收交接，不是最终数据库提交。需要持久化执行日志或更强提交确认协议才能提高这类故障的保障，但会增加延迟和复杂度。

追问 5：你的改进优先级是什么？

这是建议，不是已实现事实：优先给未确认事件缓冲加容量治理，明确写策略的强制/降级状态，完善版本部署回滚，再评估执行事件持久化的成本。不要直接宣传“换成 MQ 就所有问题都解决”。
