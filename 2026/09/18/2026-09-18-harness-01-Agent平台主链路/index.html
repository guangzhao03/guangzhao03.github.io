# 01｜Agent 平台主链路：用户一句话如何变成沙箱行动 > 核对日期：2026-09-17；源码根目录：`E:\MoreProject\learn_foresign_engine`。以下是当前工作区的静态源码讲解，不是线上部署审计或性能测试。 > > 源码采用关键片段节选，每个展示的非空源码行都附教学注释和原行号；不连续片段分别标出来源，不将伪代码冒充完整函数。注释仅在本文添加，没有改业务源码。 ## 1. 先纠正原来的概括 你原来理解的方向对，但面试必须说得更精确： 1. 当前业务编排主入口是 **SessionRunService**，AgentService 是其中的执行适配层。 2. 普通聊天主路径调用 **SandboxAgentSseService**，不是看见 bridge 文件名就认定经过 SandboxAgentBridgeService。 3. `sandbox-command-stream.service.ts` 是 PTY 终端相关链路，不是本次 Agent SSE 的主通道。 4. 正常配置下 SDK 在沙箱执行，但代码保留 Backend SDK fallback。 5. 默认使用 sbx_ 代理凭证，但保留显式直传回滚开关，不能说“源码不存在真实 Key 下发路径”。 6. Backend↔沙箱与 Backend↔浏览器有两套不同恢复序号。 ## 2. 用一个任务串起来 用户输入：“修改工作区函数并运行测试。” | 阶段 | 谁负责 | 输入/产物 | 为什么需要这一层 | |---|---|---|---| | 发消息 | 浏览器 Socket.IO | send_message、sessionId、desktopId、content | 复用已认证长连接 | | 可信入口 | SessionGateway | socket 对应身份、经过约束的请求 | 不能相信客户端自报内部权限 | | 一轮执行编排 | SessionRunService | Run 身份、消息、锁、工作树、策略、上下文 | 一次聊天包含大量业务状态 | | 模型执行适配 | AgentService | 模型连接、Skills/SubAgents 等参数 | 对上层统一执行结果 | | 沙箱桥接 | SandboxAgentSseService | endpoint、代理 token、HTTP session | 处理跨进程执行与流恢复 | | 执行 | agent-service + SDK | 真实文件/命令操作和执行事件 | 工具靠近工作区，隔离用户执行 | | 事件消费 | Backend writer/finalizer | Redis 事件流、最终 assistant 消息 | 分开处理实时恢复与长期历史 | | 展示 | 前端 store | 按 Run 与 seq 应用增量 | 避免重复、串轮次、漏尾部 | **控制面**管理“谁能做什么、在哪做、如何记账和收口”；**执行面**真正运行 SDK 与工具。两者之间不是单次 RPC 返回一个字符串，而是有创建、订阅、交互、取消、确认等控制协议。 ## 3. 建议打开这些源码 路径相对于仓库根目录。 | 入口 | 作用 | |---|---| | `packages/frontend/src/lib/socket.ts:248` | 连接 `/session` namespace | | `packages/frontend/src/lib/socket.ts:578` | 发 send_message | | `packages/backend/src/session/session.gateway.ts:432` | 握手认证 | | `packages/backend/src/session/session.gateway.ts:921` | 消息入口 | | `packages/backend/src/session/session-run.service.ts:917` | 一轮执行编排 | | `packages/backend/src/agent/agent.service.ts:284` | SDK 适配入口 | | `packages/backend/src/sandbox/application/sandbox-agent-sse.service.ts:1440` | 沙箱执行生命周期 | | `packages/backend/src/llm-proxy/llm-proxy-token.service.ts:44` | 代理 token 签发 | | `packages/backend/src/llm-proxy/llm-proxy.controller.ts:143` | 代理请求验证、转发 | | `packages/backend/src/session/stream/session-stream.store.ts:18` | Redis Lua 原子追加 | | `packages/backend/src/common/redis-io.adapter.ts:22` | 多 worker 广播 | ## 4. Gateway：认证不等于授权 浏览器连接 `/session` 时带 token。Gateway 校验 JWT，将身份关联到当前 socket；后续业务必须用这个可信身份，而不是请求体里的 userId。 握手认证只回答“你是谁”，还要校验“你是否能访问此 Desktop/Session”。join_session、join_desktop、resume_desktop_runs、stop_agent 等入口分别有资源权限检查。不要把一次握手认证说成对全部资源授权。 ### 4.1 源码逐行注释：拒绝客户端伪造内部上下文 来源：`packages/backend/src/session/session.gateway.ts:921-933`，函数后续省略。 这里示范的是**信任边界清理**，不是“检查四个字段就完成所有鉴权”。后续还会查询业务资源、解析执行上下文和权限。 ## 5. SessionRunService：一轮聊天其实是状态机 主实现：`session-run.service.ts:928` 起。 ### 5.1 关键顺序 1. 校验请求上下文，并检查是否与会话 compaction 冲突。 2. 领取 Session 执行锁；忙则返回 SESSION_BUSY。 3. **拿到执行锁后才保存用户消息**，避免失败的竞争请求落下一条永远不执行的消息。 4. 注册 AbortController、执行身份和跨实例 owner lease。 5. 准备 worktree；此阶段也能被 Stop 中断。 6. 预分配 assistantMessageId，解析可信写策略。 7. 建立 Run Stream Writer，通知执行已建立。 8. 解析积分、模型、Agent/Team、SDK resume、记忆、MCP 等配置。 9. 调 AgentService 并消费执行事件。 10. 终态保存 assistant、释放锁，再通知前端 finalized/idle。 对应位置：锁 `:1066`；用户消息 `:1160`；控制与 lease `:1246`；工作树 `:1391`；写策略 `:1492`；writer `:1620`；参数 `:3376`；执行调用 `:3454`。 ### 5.2 这几个状态不能混为一谈 - 消息已保存：数据库有用户输入。 - 执行已建立：平台已为这轮任务创建控制和事件身份。 - SDK 已启动：执行面开始处理。 - SDK FINAL：执行层已经结束。 - assistant 已持久化且锁已释放：平台已完成收口，可以安全接下一问。 如果先发 idle，再释放数据库锁，用户立即输入下一问可能得到 SESSION_BUSY。这属于跨层终态顺序问题，不是模型推理问题。 ### 5.3 必须记住的 ID | ID | 用途 | 不能替代什么 | |---|---|---| | desktopId | 稳定工作区业务身份 | 不是云实例 ID | | backend sessionId | 长期聊天容器 | 不是一次执行身份 | | userMessageId | 这一轮 Run 的业务锚点 | 不是 SDK messageId | | assistantMessageId | 预分配并最终持久化的回答身份 | 不能终态又创建另一条回答 | | executionLockToken | 区分当前执行 owner 与陈旧执行 | 不是模型 API token | | sandbox sessionId | 沙箱内一次执行与 SSE 通道 | 不是 SDK resume 身份 | | sdkSessionId | SDK 历史续接 | 不是 SSE 游标 | | sandboxEventId | 沙箱到 Backend 私有流序号 | 不是浏览器应用序号 | | seq | 平台 Run 增量协议序号 | 不是全系统全局消息顺序 | ## 6. 找到正确沙箱，再建立 HTTP/SSE AgentService 默认进入 SandboxAgentSseService，后者从 Desktop 映射得到 provider 与 sandboxId，再解析 7777 服务端点。它不是把 SSE 搬到 SDK 命令通道中传输。 ### 6.1 源码逐行注释：endpoint 解析 来源：`packages/backend/src/sandbox/application/sandbox-agent-sse.service.ts:1059-1063`。 来源：同文件 `:1065-1076`。 **为什么值得讲？** 冷重建会改变 sandboxId，但正在运行的内存 session 不会自动搬到新容器；不能每次请求都无脑按 Desktop 最新映射路由。 ### 6.2 创建与执行时序 POST /sessions 只返回 created；GET events 成功绑定后，沙箱才 start/query。详细源码见 [第三份 Runtime 文档](03-沙箱内Agent-Runtime.md)。用户问答使用 respond；取消使用 abort；ACK 另走确认接口。 ## 7. LLM Proxy：真实 Key 代持，而非“没有凭证” 模型调用是另一条子链路： 沙箱 SDK → Backend LLM Proxy → SmartAPI/上游模型 → 流式响应。 沙箱配置的 ANTHROPIC_API_KEY 默认是 sbx_ token；ANTHROPIC_BASE_URL 指向 Backend Proxy。沙箱 7777 网关访问 headers 与 sbx_ 是**两种不同凭证**：前者访问 Runtime，后者访问模型代理。 ### 7.1 源码逐行注释：签发 opaque token 来源：`packages/backend/src/llm-proxy/llm-proxy-token.service.ts:52-63`。所属 create 方法的参数为 desktopId、employeeId、tenantId 及可选连接信息。 当前 Proxy controller 实际转发使用 `smartApiAccessService.baseUrl/serviceKey`，不能因为 token payload 保留 modelApiKey 字段，就说必然优先使用它。引用：`llm-proxy.controller.ts:210`、`:234`。 ### 7.2 源码逐行注释：避免吊销后被续期复活 来源：`llm-proxy-token.service.ts:101-112`，已省略之前读取 token 和过期检查。 默认执行中每小时尝试续期，失败后较短间隔再尝试；执行完成或启动失败会主动 revoke。3 小时相对长期服务 Key 属于短效，不要讲成“每几分钟换一次”。 **边界：**临时 token 仍然是能力凭证，不能泄露；撤销只影响后续授权，不撤销已完成工具副作用。默认 Key 隔离也不等于沙箱没有 Git、MCP 等其他凭证。 ## 8. 两层事件恢复，解决两类断线 ### 8.1 第一层：沙箱到 Backend 作用：Backend HTTP 连接短时中断，重连同一 Runtime 执行。 - 沙箱 eventSequence 编号。 - Backend 维护最高连续接收 ID。 - Last-Event-ID 回放，POST ACK 清理内存缓冲。 - 终态有限保留，Runtime 重启后不保证恢复。 来源：`sandbox-agent-sse.service.ts:628-640`。 来源：同文件 `:649-657`。 ### 8.2 第二层：Backend 到浏览器 作用：浏览器刷新、跨 worker 重连或发现展示事件缺口。 Backend 为 Run 维护单调 seq，Redis Stream 保存有界增量，snapshot 保存可恢复状态。浏览器按 userMessageId + assistantMessageId + seq 应用事件。 写入 Redis 和 seq 分配通过 Lua 在 Redis 内原子执行。这能避免旧 owner 污染新执行，也避免多个命令之间出现“序号更新了但事件还没追加”的可见窗口。**原子性仅限此脚本，不包含外部数据库和工具操作。** ### 8.3 源码逐行注释：Redis 追加前的 owner 与重复检查 来源：`packages/backend/src/session/stream/session-stream.store.ts:19-31`。下方展示模板字符串内的原 Lua 语句。 来源：同文件 `:38-49`；之前还校验协议版本和 Run 身份。 默认 running TTL 1 小时，终态通常 30 分钟，特殊收口失败保留更久；Stream 近似保留 10000 条。它是恢复日志，不是永久聊天历史。 ## 9. Redis 有三个职责，不要只说“用了 Redis” | 机制 | 问题 | 是否保存历史 | |---|---|---| | Socket.IO Redis Adapter | 执行在 A，但浏览器连 B，如何广播 | Pub/Sub 不为离线客户端保存历史 | | Run Redis Stream + snapshot | 浏览器漏事件、刷新，如何补状态 | 有界、带 TTL | | execution owner lease + 控制通知 | Stop/人工回答应该送给哪个 worker | 保存控制状态，非聊天历史 | ### 9.1 源码逐行注释：跨实例适配器 来源：`packages/backend/src/common/redis-io.adapter.ts:23-25`，就绪等待部分省略。 来源：同文件 `:39` 与 `:43-47`，为两个独立片段。 浏览器恢复时先 join room，再读恢复水位，允许实时和回放重复，由 seq 去重，避免两个阶段之间形成漏事件空窗。 ## 10. 失败场景怎么解释 | 场景 | 当前处理 | 不应夸大的点 | |---|---|---| | 同 Session 并发发送 | 执行锁拒绝第二个请求 | 不是给每条用户消息自动排队 | | 浏览器断线 | 不直接取消 SDK，可后台继续 | 依赖保留窗口恢复，不是永久重放 | | 私有 SSE 断线 | 重接原执行并回放 | 不等于重跑 prompt | | 恢复窗口耗尽 | 无 FINAL 则显式失败，尝试 abort | socket close 不等于成功 | | 用户 Stop | owner 定位、AbortController、远端 abort | 取消后保留短窗口收 usage/FINAL | | Redis 写流失败 | writer 可 degraded，继续本机广播 | 跨实例恢复保证会下降 | | Backend owner 改变 | execution token 限制旧执行收口/写流 | DB、Redis、外部 API 不在一个事务里 | | 终态 assistant 保存失败 | 走失败收口与恢复路径 | 模型结束不代表平台持久化成功 | 平台超时见 `packages/backend/src/session/session-execution.constants.ts:6`：首事件 3 分钟、不活跃 30 分钟、最大 10 小时。首事件不是严格首 token 指标，heartbeat 也不能无限掩盖启动卡住。 ## 11. 面试表达模板 ### 一分钟版 > 一次聊天在我们平台中是一条跨进程流水线。前端通过 Socket.IO 到 Gateway，服务端把连接身份转成可信执行上下文；SessionRunService 负责锁、消息、工作树、写策略和 Run 身份，AgentService 统一模型执行参数，SandboxAgentSseService 将任务交给沙箱内 SDK。工具在沙箱就地执行，事件先经私有 SSE 回 Backend，再经 Redis Run Stream 和 Socket.IO 回浏览器。我们把两层断线恢复分开，并用执行 token 防止旧 owner 污染当前轮次；模型凭证默认由 Backend 代持，只下发可续期、可吊销的临时代理 token。 ### 追问：你的核心工程难点是什么？ 选择讲三个，而不是罗列十几个类： 1. **执行身份和状态收口**：并发发送、Stop、人工回答不能串到另一轮。 2. **两层可靠交付**：私有 SSE 回放与浏览器 Stream/snapshot 分开，明确 ACK 的保障边界。 3. **凭证治理**：真实 Key 代持、用户权限透传、token 续期与结束吊销。 ### 追问：是不是 exactly-once？ 不是。源码包含事件去重、连续序号、owner fencing、幂等收口等局部保证，但私有 ACK 并非数据库提交确认，工具副作用也不在 Redis 事务里。准确目标是有限窗口下恢复、有序应用和防止陈旧执行污染。 ### 追问：有哪些指标能证明效果？ 应真实采集：执行建立耗时、首业务事件耗时、SSE 恢复成功率、浏览器补流次数、终态落库延迟、锁冲突率、代理鉴权失败率。源码不能推导出生产百分比；简历里没有实测就不要写“零丢失”“性能提升 80%”。 ## 12. 复习验收 -
