02｜双 Provider 沙箱抽象：同一套业务如何支持两套执行环境

# 02｜双 Provider 沙箱抽象：同一套业务如何支持两套执行环境 > 核对日期：2026-09-17。代码根目录：`E:\MoreProject\learn_foresign_engine`。结论依据当前工作区实现，不等于所有线上部署已经采用相同配置。 > > 本文选取关键源码逐行解释，行尾注释为教学添加。代码块是节选，不代表完整文件；所有源码引用都相对于仓库根目录。没有修改业务代码或创建云端资源。 ## 1. 面试前先修正三个事实 | 原先的概括 | 当前源码所表现的实现 | 面试应该怎么说 | |---|---|---| | OpenSandbox 用 PVC 持久化工作区 | workspace 当前挂载 hostPath | 自建 K8s 工作区采用节点本地目录，恢复需要考虑节点绑定 | | 腾讯没有 pause/resume | 优先 platform pause/connect，必要时才降级 | 能力不对等时采用能力适配与冷恢复 | | 腾讯工作区在 COS | Registry 当前装配 CfsVolumeProvider | 使用 CFS 子路径承载工作区，旧 COS 注释不代表当前装配 | **为什么要强调？** 面试官问“Pod 调到另一个节点文件还在吗”，hostPath 和网络文件系统的答案完全不同。把它们统称为“持久卷”而不说明存储语义，会掩盖真正的设计约束。 ## 2. 核心抽象不是两个 SDK，而是三种身份 以一个 Desktop 为例： | 身份 | 示例概念 | 是否应随冷重建变化 | |---|---|---| | desktopId | 用户看到的稳定工作空间 | 不变 | | sandboxId | 当前云平台计算实例 | 可以变 | | volumeName | 工作区持久存储命名，通常 workspace-桌面ID | 尽量不变 | 数据模型位置：`packages/backend/prisma/schema.prisma:341`。 冷恢复的本质是：**为同一个业务 Desktop 更换计算实例，重新关联已有工作区。** 这不是把一个正在运行的进程迁移到另一个云，更不是保证内存和连接继续存在。 业务服务通常拿 desktopId；缓存解析出 `{ sandboxId, provider }`；连接池按 provider 和 sandboxId 找执行连接；文件/命令走统一接口。 ## 3. 阅读地图 | 源码位置 | 关注点 | |---|---| | `packages/backend/src/sandbox/infrastructure/runtime/sandbox-provider.types.ts:22` | provider 归一化 | | `packages/backend/src/sandbox/infrastructure/runtime/sandbox-provider.registry.ts:22` | Registry 运行时查找 | | `packages/backend/src/sandbox/sandbox.module.ts:92` | 两套能力如何装配 | | `packages/backend/src/sandbox/infrastructure/runtime/sandbox-runtime.provider.ts:67` | 文件、命令、连接能力 | | `packages/backend/src/sandbox/infrastructure/runtime/sandbox-manager.provider.interface.ts:29` | 暂停、恢复、销毁等管理能力 | | `packages/backend/src/sandbox/infrastructure/volume/volume-provider.interface.ts:18` | 持久工作区能力 | | `packages/backend/src/desktop/desktop.service.ts:583` | Desktop 创建时选择渠道 | | `packages/backend/src/sandbox/application/sandbox-lifecycle.service.ts:206` | 创建步骤与失败补偿 | | `packages/backend/src/sandbox/application/sandbox-lifecycle.service.ts:443` | 启动/恢复的状态分支 | | `packages/backend/src/sandbox/application/sandbox-lifecycle.service.ts:655` | 冷重建 | | `packages/backend/src/sandbox/infrastructure/tencent/tencent-sandbox.adapters.ts:187` | 命令返回语义适配 | ## 4. Registry、Strategy、Adapter 分别解决什么 不要只背“这里用了 Registry 模式”。这里三种思想同时存在： - **Registry**：按 provider 名字查出一组对象，解决“运行时去哪里拿实现”。 - **Strategy**：runtime、manager、volume 有可替换实现，解决“同一个业务动作选择哪套行为”。 - **Adapter**：腾讯 SDK 的返回值、错误模型、端点访问方式被转换成平台接口，解决“外部语义如何对齐”。 Registry 本身不实现暂停、文件读写，也不负责自动抹平两家能力差异。 ### 4.1 源码逐行注释：注册表查询 来源：`packages/backend/src/sandbox/infrastructure/runtime/sandbox-provider.registry.ts:38-52`。 `normalizeSandboxProvider` 当前只有精确值 tencent 走腾讯，其余值回退 opensandbox。它不是严格的非法值拒绝器；外部输入是否严格校验要看调用边界。 ### 4.2 源码逐行注释：装配决定了“当前用什么存储” 来源：`packages/backend/src/sandbox/sandbox.module.ts:99-109`。 来源：同文件 `:111-132`。 PTY 工厂还有惰性 resolver 回填，避免 Registry → ConnectionPool → PTY Factory → Registry 的构造期循环依赖。它是依赖装配问题，不是厂商网络请求问题。 ## 5. 为什么叫“窄接口” 上层只依赖所需能力，而不把整个 SDK 类型散落到业务服务。接口不是对所有厂商 API 的一比一复制；但当前形状有意沿用 OpenSandbox，减少既有调用方迁移成本。 ### 5.1 源码逐行注释：文件接口 来源：`packages/backend/src/sandbox/infrastructure/runtime/sandbox-runtime.provider.ts:67-75`。 ### 5.2 源码逐行注释：命令接口 来源：同文件 `:80-95`。 ### 5.3 Adapter 的工程含量在语义，而不是改名 | 差异 | 适配方式 | 代价/限制 | |---|---|---| | 命令非零退出 | 腾讯 SDK 可能抛带 stdout/stderr/exitCode 的异常，适配成普通 CommandResult | 网络异常仍应抛出，不能全部吞掉 | | 端点访问 | 返回 URL 与 headers，而不只 URL | 业务客户端必须透传正确网关认证信息 | | 命令 session | 腾讯侧主要通过 cwd 模拟 | 不保证 export/cd 等 shell 内存状态跨命令保留 | | 指标 | 腾讯 ConnectedSandbox metrics 当前为空对象 | 接口存在不代表实际指标齐全 | | 创建规格 | 腾讯资源档位映射 templateId | 不是任意传 cpu/memory 就能生效 | | 节点管理 | OpenSandbox 有节点解析和钉定；腾讯没有这层能力 | 可选能力不能假装完全一致 | **面试答法：统一的是业务调用契约，尽量集中语义差异，不是证明所有云能力等价。** ## 6. Desktop 如何决定 provider 创建时：DesktopService 归一化 provider → 检查 available → 处理腾讯规格/审批 → 落库 → provisionContainer 从数据库读取 provider 和规格 → lifecycle 选择相应实现。 已有 Desktop 执行命令时：desktopId → SandboxIdCache 查 `{sandboxId, provider}` → provider-aware 连接池 → Registry → ConnectedSandbox.files/commands。 关联源码： - Desktop 创建：`packages/backend/src/desktop/desktop.service.ts:583-605`。 - provision：同文件 `:1067-1154`。 - 缓存：`packages/backend/src/sandbox/application/sandbox-id-cache.service.ts:84-117`。 - 连接池：`packages/backend/src/sandbox/application/sandbox-connection-pool.service.ts:146`、`:520`。 缓存冷重建后要失效。只改数据库、不失效多副本缓存，会让其他 worker 继续操作旧实例。这里既有 ID 缓存，也有每个进程自己的连接对象，不能把两者当成一个 Redis key。 ## 7. 存储：hostPath 与 CFS 真正区别在哪 ### 7.1 源码逐行注释：OpenSandbox 工作区挂载 来源：`packages/backend/src/sandbox/infrastructure/opensandbox/sdk-connection.config.ts:193-201`。 共享 Gradle 缓存另有 hostPath/PVC 选项，不要把它的 PVC 分支套到 workspace 上。 K8sVolumeProvider 会通过 workspace-cleaner 准备目录/权限、清理目录，并能查询节点、钉定 BatchSandbox。上方旧注释写“未实现钉定”也应与当前实际方法对照；不能只读注释当最终事实。 **关键限制：**相同路径在不同节点上可能是完全不同的数据。原实例 pause/resume 的节点钉定，不等于创建新实例时已经把旧节点约束传进去。 ### 7.2 腾讯 CFS 的子路径隔离 腾讯模板定义 CFS StorageMount，实例通过 x-mounts metadata 选择 `subPath=volumeName`。Backend 用 bootstrap 沙箱准备子目录，再让业务实例挂载。 关联源码： - `packages/backend/src/sandbox/infrastructure/tencent/tencent-connection.config.ts:292-337`。 - `packages/backend/src/sandbox/infrastructure/tencent/cfs-prefix.bootstrapper.ts:30-145`。 - `packages/backend/src/sandbox/infrastructure/volume/cfs-volume.provider.ts:12`。 为什么选 CFS？Git 工作区需要接近 POSIX 的权限、目录和文件锁语义，不能只看到“云存储”就把对象存储等同于普通文件系统。 CFS 当前 delete 实现并未真正执行工作区删除。因此“业务 Desktop 删除完成”和“所有存储数据已经物理清除”不能划等号。这是数据生命周期需要完善的地方。 ## 8. pause/resume：先原地恢复，再考虑重建 ### 8.1 源码逐行注释：腾讯 pause 的能力分支 来源：`packages/backend/src/sandbox/infrastructure/tencent/tencent-sandbox-manager.provider.ts:115-138`。为避免引用过时 COS 文案，以下分成两个真实片段，省略 catch 内日志部分。 此处 catch 范围包含所有 pause 错误，不只是平台明确“不支持”。报告边界时应说实际行为，而不是把注释解释成严格错误分类。 resume 中 platform 使用 Sandbox.connect 唤醒 paused 实例；遇到明确不存在则抛 ColdResumeRequiredError，由 lifecycle 接管重建。不能用“404 一律删除 Desktop”处理，因为腾讯还可能以特殊 404 文案表达 paused 状态。 ### 8.2 业务状态与云状态 常见归一映射：Creating→creating，Running→running，Pausing→stopping，Paused→stopped，Resuming→starting，Deleting→deleting，Deleted→deleted。Terminated 或特定容器退出失败可以映射为停止后可恢复。 startRuntime 会区分： - 已 Running：不重复 resume。 - Resuming：等待完成。 - Paused：resume 后等 Running。 - Pausing：先等待停止，再恢复。 - Terminated/特定已退出状态：尝试冷重建。 - 真正 missing：结合 provider、业务状态和冷恢复配置判断，不是一律重建。 stopRuntime 的迟到回调不能把 deleting 改回 stopped，因此有条件状态更新。这是生命周期并发控制，与 SDK API 参数适配是两类问题。 ## 9. Cold Resume 完整拆解 ### 9.1 先尝试领取重建权 来源：`packages/backend/src/sandbox/application/sandbox-lifecycle.service.ts:669-676`。 **不要直接背原注释中的“绝不能再次创建实例”。** 如果输入 status 已经是 starting，条件不一定构成一次性转换；数据库更新和云端创建也不是同一个事务。这是实现防重建竞争的机制，不是所有故障下的 exactly-once 证明。 ### 9.2 复用工作区、更换计算实例 来源：同文件 `:703-720`，省略原有旧 COS 注释。 之后还有：腾讯实例 TTL 跟踪 → 失效旧 ID/连接缓存 → 尽力清理旧实例 → finalizeRunning → 更新配置与活动状态。 ### 9.3 能保留什么 | 状态 | 冷恢复是否保留 | 原因 | |---|---|---| | CFS 挂载里的工作区文件 | 通常可以 | 存储独立于计算实例 | | 工作区中的 Git 对象 | 取决于是否在保留挂载中 | 属于文件状态 | | 正在运行的 SDK/命令 | 不保留 | 进程已经终止 | | Shell export 等内存状态 | 不保留 | 不是文件系统内容 | | 原 HTTP/SSE 连接 | 不保留 | 连接绑定旧进程/端点 | | Backend 数据库聊天记录 | 不受实例重建直接影响 | 控制面持久化独立存在 | | hostPath 跨节点数据 | 不能仅凭相同 volumeName 保证 | 不同节点本地磁盘不同 | ## 10. 创建失败补偿与恢复失败补偿不能盲目复用 正常新建失败：清理刚创建的实例和卷，看起来合理。 恢复旧工作区失败：如果复用同一 provisioning 方法，把幂等 volume.create 也视为“本次创建的新卷”，后续失败补偿可能误处理旧数据。当前源码的统一流程存在这类语义边界，需要区分**新建资源所有权**与**复用既有资源**。 相关位置：`sandbox-lifecycle.service.ts:233-236`、`:297-304`、`:705-712`。 面试可将其作为审慎的改进方向：明确资源是否由本次流程创建，补偿仅回收本次拥有的资源；不要把“所有异常都 delete”称为完善回滚。本文没有执行破坏性验证，也没有修复这些路径。 ## 11. 抽象的裂缝，要坦诚而不是回避 1. lifecycle 仍有腾讯专属错误与规格解析分支，不是全项目零 if-else。 2. 命令 session、metrics、interrupt 等能力并不完全等价。 3. hostPath 节点约束与 CFS 挂载语义无法用一个 volumeName 自动解决。 4. CFS 实际清理语义仍不完整。 5. 仍有旧默认 provider 注入路径，不能说所有调用方都已完全迁移。 6. 模板资源档位、平台续期等能力仍带明显厂商特征。 抽象价值是**将差异集中在较少且可解释的地方**，不是让差异消失。 ## 12. 面试表达与追问 ### 一分钟版 > 我们将 Desktop 业务身份、sandbox 计算实例和 workspace 存储身份分开。Backend 同时装配 OpenSandbox 与腾讯 AGS，根据 Desktop.sandboxProvider 通过 Registry 选择 runtime、manager、volume 和 PTY；文件、命令和端点使用统一窄接口。适配的难点不是替换 SDK 名称，而是命令异常、端点鉴权、模板规格、暂停能力与存储语义。无法原地恢复时重新创建计算实例并挂回原工作区，同时刷新跨副本缓存；代价是内存态丢失。当前 OpenSandbox 用 hostPath，腾讯用 CFS，恢复保障不能一概而论。 ### 问：为什么不写两个独立业务服务？ 会让会话、文件、工具、恢复逻辑重复，日后修复容易漂移。通过共同接口复用通用业务，厂商适配集中维护；但统一接口也需要清楚表达可选能力或降级，不应制造虚假一致性。 ### 问：为什么不自动从腾讯切到 OpenSandbox？ provider 选择与存储位置、模板配置、网络端点、配额和数据迁移相关。当前冷恢复仍在原渠道重新创建，不是自动跨云故障切换。跨云需要单独的数据复制和一致性方案。 ### 问：资源规格为什么映射模板？ 腾讯侧资源规格固化在预建模板中，简单传 CPU/内存参数可能不生效。因此业务规格需要映射到有效模板，缺失要明确报错，而不是静默退回默认规格。 ### 问：抽象有没有过度设计？ 已有两个真实渠道和大量通用调用方，存在明确复用需求；接口形状沿用既有 SDK，优先控制改造成本。未来是否再拆能力，要看新的真实需求，而不是先做一个万能云框架。 ## 13. 自测与继续阅读 - 用不超过 30 秒解释三个身份为什么分开。 - 不看表格说出两家接口形状一样但语义不同的三个例子。 - 解释为什么 hostPath 冷重建不能只看 volumeName。 - 说明 Registry 和 Adapter 谁负责厂商差异。 - 说明数据删除、实例删除、暂停分别影响什么。 - 能否把“设计已实现”与“改进建议”分开表达？ 结合 [01｜主链路](01-Agent平台主链路.md) 看 Provider 如何服务一次聊天，再读 [03｜Runtime](03-沙箱内Agent-Runtime.md) 了解实例内的执行。
