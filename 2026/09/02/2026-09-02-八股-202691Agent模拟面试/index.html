# Agent 日常实习模拟面试复盘(2026-09-01) > 覆盖范围:Agent 基础 / Tool Use / Memory / Multi-Agent / 工程与评估 / 开放设计 > 个人强弱项:机制理解强(Tool Use、Memory),短板在 Multi-Agent 模式、评估方法、术语准确性 --- ## 一、Agent 基础 ### Q1 什么是 Agent?与普通 LLM 调用的区别 - **本质区别:控制流由谁决定。** 普通 chain = 开发者写死流程;Agent = 模型根据观察动态决定下一步 - 工具/记忆只是能力组件,不是本质 - 一句话:**Agent = 模型驱动的控制流**(LLM + harness) ### Q1.2 什么情况下不用 Agent,用 workflow - 判断标准:流程能否预先规则化 - 用 workflow:结构化抽取(发票/简历)、高风险合规场景(可审计可复现)、批量成本敏感任务、意图路由(分支可枚举) - 用 Agent:步骤数不可预知(修 bug、调研)、开放式任务 - 原则(Anthropic):**用能解决问题的最简单方案** ### Q2 Agent Loop 基本流程 - 四要素:消息历史、模型调用、工具执行器、终止条件 - 术语纠正:不是"死锁",是**无限循环**(重试上瘾/来回打转)→ 需要 max_steps 硬上限 - ⚠️ 易错点:工具结果必须回填 messages,否则模型看不到结果 ### Q2.2 max_steps 用尽还没完成,怎么兜底 ⭐(答得好,记这个思路) - **先归因,再对症**: 1. 循环/注意力漂移(忘了任务)→ 重注入任务提示纠偏后继续 2. 任务本身大 → 压缩/总结上下文保留进度续跑 - 全程保留中间产物;多次续跑失败才升级报错/转人工 - 归因可自动化:让模型自我诊断(打转 or 任务大) ### Q3 ReAct vs CoT - **CoT = 闭卷考试**:只靠参数知识推理,接触不到真实信息,错了没法纠正、一路滚到底(幻觉来源) - **ReAct = 开卷 + 有反馈**:Thought → Action → **Observation(真实结果)** → 修正 - 关键词:**grounding(观察锚定推理)**、计划可动态调整 - 记忆:CoT 想好再做错到底;ReAct 边做边看边修正 - ⚠️ 我的错误归因:"CoT 噪声多"——不对,CoT 的问题是接触不到外部信息、无反馈纠正 ### Q4 Plan-and-Execute vs ReAct - Plan-and-Execute:先全局规划再逐步执行 → 适合**依赖关系清晰的大任务**(写报告) - ReAct:走一步看一步 → 适合**探索型任务**(调试 bug,下一步取决于观察) - Trade-off:计划基于旧信息,执行中发现错了**重规划代价高**;ReAct 灵活但短视 - 生产常用**混合**:粗规划 + ReAct 执行 + 偏离时重规划 --- ## 二、Tool Use / Function Calling ### Q5 Function Calling 底层原理 ⭐(答得好) - 工具定义(name + description + 参数 schema)随请求发给模型 = 只是注入的文本 - **模型从不执行工具,只输出"我想调用 X + 参数 Y"的结构化 JSON** - 执行、安全、重试全在 harness 侧;结果回填 messages 再发模型 - 本质:**模型是结构化输出生成器**,只点菜,执行权在外部 ### Q5.2 工具太多(上百个)怎么办 - 问题:①description 撑爆 token ②相似工具选择困难 - 解法: - **Tool Retrieval(工具检索)**:description 做 embedding,按请求动态召回 top-K 注入(MCP、Claude Code 的 ToolSearch 都是这个) - description 工程化:写清何时用/不用、与相似工具的区别 - 参数 schema 简洁:参数少、默认值、嵌套浅 ### Q7 工具调用失败怎么处理 - **失败也是 Observation**:try-catch 住,报错作为 Observation 塞回 messages,模型自己调整 - 报错要**可行动(actionable)**:`File not found: /data/users.csv. Available files: [a.csv, b.csv]`(原因+建议+线索),不能只给 `Error` - **重试上限**:同一工具连续失败超限 → 强制干预(注入"停止重试"或终止),防模型重试上瘾 - 错误分类:harness 先过滤——可重试(429/超时)指数退避自动重试;不可重试(参数错)才回传模型 ### Q8 工具 description 设计 - 该有:①做什么 ②何时用/不用(边界声明,最有效)③与相似工具的区别 ④参数格式约束示例 ⑤返回什么 - 避免:空泛描述、实现细节泄漏(模型不关心)、参数堆砌 - 加分:description 也是 prompt,**可按误调用案例迭代优化** --- ## 三、Memory 与上下文 ### Q9 短期记忆 vs 长期记忆 - 短期:messages 列表,会话内 → 本质是**上下文管理**(压缩/截断/外部化) - 长期:跨会话,落盘为 Markdown 文件(如 Claude Code memory)/向量库 → 本质是**检索系统**(按相关性召回注入,不全量塞) - 统一约束:**窗口有限,什么值得占 token** ### Q10 上下文压缩策略 ⭐(答得好,逐级降级) 1. **外部化**:中间产物落盘,留占位符按需读取(信息不丢) 2. **裁剪中段保头尾**:头=任务定义/系统指令,尾=最新进展 3. 工具结果 → 占位符 4. 硬裁剪按 token(最后手段) - **绝不能丢**:系统指令+任务目标、关键决策及理由、用户约束、当前进度 - 摘要是**有损压缩**,高级做法:分层摘要 + 原文可回溯 - **水位线触发**(如 80%),不要爆了才压 ### Q11 多轮长任务遗忘关键信息,根上解决 - 本质:**遗忘不是记忆问题,是信息架构问题**——信息被挤出上下文了 - 三层方案: 1. **常驻层**:关键约束写进 system prompt(每轮可见)——**常驻优于定时重注入** 2. **结构化状态层**:显式状态文档/scratchpad,压缩时必保 3. **外部化层**:CLAUDE.md / memory 文件 - ⚠️ "每 N 轮重注入"有隐患:中间窗口照样跑偏,N 不好定 --- ## 四、Multi-Agent(短板,重点补) ### Q12 什么时候用多 Agent - **本质价值:上下文隔离,不只是并行提速**(⚠️ 我只答了效率,漏了核心) - 单 Agent 杂活多 → 上下文污染、注意力稀释;多 Agent 子上下文独立干净,只回传结论 - 优势:①上下文隔离 ②并行 ③故障隔离 ④子 Agent 可用不同模型/prompt - 劣势:①通信有损(子看不到全局)②token 翻倍 ③协调复杂 ④调试难 - 判断标准:子任务真正独立(DAG 无边)、主上下文装不下才值得;强耦合任务拆开反而更慢更贵 ### Q13 多 Agent 通信与协调(没答上,背下来) - **主流模式:Orchestrator-Workers(编排者-工作者)**: - 主 Agent 拆任务 → 每个 Worker 独立上下文执行 → 只回结果摘要 → 编排者决定继续派活/收工 - **Worker 互不通信,全部经编排者中转**(中心化,不是总线) - Claude Code subagent、Anthropic 多 Agent 研究系统都是这个 - 次要模式:Agent-to-Agent 流水线(生成→评审→修复),链长误差累积 - 通信本质:**结构化文本交换,没有魔法** - 协调难点:任务粒度、结果格式约定、冲突仲裁(同一文件唯一 owner) --- ## 五、工程与评估(短板,重点补) ### Q14 Agent 死循环/跑偏/不稳定,怎么调试 - 第一步:**可观测性先行**(LangSmith/Langfuse trace:每轮 messages、工具调用、token、耗时) - 第二步:**按症状归因**(这张表要背): | 症状 | 根因 | 治法 | |---|---|---| | 死循环 | 重试上瘾;结果没回填 | 失败计数干预;检查回填;description 写"何时停" | | 跑偏/忘任务 | 目标被挤出上下文 | 目标常驻 system prompt;中途重注入 | | 输出不稳定 | 温度/prompt 模糊/无 schema 约束 | 低温;few-shot;structured output | | 工具选错 | description 模糊重叠 | 边界声明;消歧义 | - 第三步:坏 case 固化成**回归测试集**,防修一个坏两个 ### Q15 怎么评估 Agent ⚠️ 必考,优先背 - **三维指标**: 1. **结果**:成功率(N 个测试任务达标几个);判定:人工 / LLM-as-judge(按 rubric 打分) / 程序化校验 2. **过程(Trajectory)**:路径效率(3 步能完成却绕 15 步)、工具选择对不对、有无多余危险操作 3. **成本**:平均轮数、token、延迟、单任务成本 - **方法**:建评估集(几十~几百个代表性任务,版本化)→ LLM-as-judge 打分(judge 要抽查校准)→ golden set 人工抽检防漂移 - 一句话:**结果、过程、成本三维;评估集 + LLM-as-judge + 人工校准** ### Q16 延迟和成本优化 - 开场白先说"**先测量再优化**"(trace 看 token 花在哪),再给手段: 1. **模型分层路由**:简单步骤(工具调用/格式化)用小模型,关键决策用强模型 2. **Prompt Caching**:系统提示/工具定义每轮重复发送,缓存降 90%,Agent 场景命中率天然高(必答点) 3. **减少轮数**:单轮并行多工具调用;高频操作封装复合工具/skill;early exit 4. **上下文瘦身**:压缩/落盘/占位符 5. 流式输出(体感) --- ## 六、开放设计题 ### Q17 订机票+酒店 Agent ⭐(答得好) - 我的答案(正确):Agent Loop 主干 + 查询(list)/下单(commit)工具分离 + 支付前人工确认(human-in-the-loop) - 补全架构: - **状态管理**:多目标任务有依赖(机票定了才定酒店),显式任务状态/plan,不靠上下文记 - **约束继承**:时间/预算/偏好常驻 system prompt - **两段式下单**:`create_order`(锁价)→ `confirm_and_pay`(用户确认后)——人工确认做成流程而非弹窗 - **失败路径**:报错可行动回传改备选;超时未支付要能**取消/回滚**,不留僵尸订单 ### Q18 从零搭 Coding Agent - 我答到的:Agent Loop、bash 工具、上下文压缩、memory、subagent、task/todo 系统(= Claude Code 真实架构) - 补的: 1. **权限与安全层**(最大难点:能改真实文件跑真实命令)——写文件可自动,`rm -rf` 必拦 2. **专用工具 > 万能 bash**:Read/Edit/Grep 单独工具 schema 和报错更可控,省 token 3. **计划机制**:plan mode,用户确认再动手 4. **可验证闭环**:改完 → 跑测试 → 看结果 → 再修(结果可自动验证是 Coding Agent 可靠的原因) --- ## 📌 优先补的三件事 1. **背 Q15 评估框架**(结果/过程/成本三维 + 评估集/judge/人工校准)——必考 2. 读 Anthropic 两篇博客(补四、五部分): - *Building effective agents* - *How we built our multi-agent research system* 3. 过一遍 Q14 症状归因表 ## 📌 高频一句话弹药 - Agent = 模型驱动的控制流 - 模型只产 JSON,执行在 harness - 遗忘是信息架构问题:常驻优于定时注入 - 压缩 = 信息分级:落盘可回溯 → 结构性必保 → 其余摘要裁剪 - 多 Agent 的本质价值是上下文隔离 - 评估三维:结果、过程、成本 - 先测量再优化
