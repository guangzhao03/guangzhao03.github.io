# day4 - 静态资源：服务器上存储的不会改变的数据，通常不会根据用户的请求而变化。比如HTML、CSS、JS、图片、视频等 - 动态资源：服务器根据用户请求和其他数据动态生成，内容可能会在每次请求时都发生变化。比如Servlet、JSP等（负责逻辑处理）Spring框架。 Web服务器（Tomcat） - B/S架构：Browser/Server，浏览器/服务器架构模式。客户端只需浏览器，应用程序的逻辑和数据都存在服务器端（维护方便，体验一般） - C/S架构：Client/Server，客户端/服务器架构模式。需要单独开发维护客户端（体验不错，开发维护麻烦） ## Spring - 官网：spring.io - Spring发展到今天已经形成了一种开发生态圈，Spring提供了若干个子项目，每个项目用于完成特定的功能。 Spring Boot可以帮助我们非常快速的构建应用程序，简化开发、提高效率。 ### 入门程序 - 需求：基于SpringBoot开发一个web应用，浏览器发起请求/hello之后，给浏览器返回一个字符串“Hello Xxx”。 1、创建springboot工程，并勾选web开发相关依赖 2、定义HelloController类，添加方法hello，并添加注解。 3、运行启动类，测试。 - Spring 官方脚手架连接不上解决方案 换成start.aliyun.com换成阿里云的url #### 入门程序解析 起步依赖： - spring-boot-starter-web：包含了web应用开发所需要的常见依赖 - spring-boot-starter-test：包含了单元测试所需要的常见依赖 - 官方提供的starter ## HTTP协议 - 概念：Hyper Text Transfer Protocol 超文本传输协议，规定了浏览器和服务器之间数据传输的规则。 - 特点： - 基于TCP协议：面向连接，安全 - 基于请求-响应模型：一次请求对应一次响应 - HTTP是无状态的协议：对于事务处理没有记忆能力。每次请求- 响应都是独立的。 - 缺点：多次请求间不能共享数据 - 优点：速度快 ### HTTP请求协议 请求行（数据第一行）：（请求方式、资源路径、协议） 请求头：第二行开始 ，格式key：value 请求体：POST请求，存放请求参数，和请求头有一行隔开 #### 请求数据获取 - Web服务器（Tomcat）对http协议的请求数据进行解析，并进行了封装（HttpServletRequest），在调用Controller方法的时候传递给了该方法，这样，就使得程序员不必直接对协议进行操作，让Web开发更加便捷。 ### HTTP响应协议 响应行 响应头 响应体 响应码：5类 1xx 响应中-临时状态码 2xx 成功 3xx 重定向 4xx 客户端错误 5xx 服务端错误 #### 响应数据设置 - Web服务器对HTTP的响应数据进行了封装（HttpServletResponse），并在调用Controller方法的时候传递给了该方法。这样，就使得程序员不必直接对协议进行操作，让Web开发更加便捷。 1、HttpServletResponse封装 2、ResponseEntity封装 ## SpringBootWeb案例 项目开发中，我们建议用基本类型包装类去定义，因为默认值的问题（用基本数据类型0可能是默认值也可能是真0） ResponseBody注解：将我们的controller的返回值直接作为响应体的数据直接响应，如果返回值是对象/集合可以转json再响应过去。 ### 分层解耦 #### 三层架构 - 三层架构 数据访问，逻辑处理，接收请求、响应数据 单一职责原则让每一个接口每一个方法，每一个类只管一个功能。 - controller：控制层，接收前端发送的请求，对请求进行处理，并响应数据 - service：业务逻辑层，处理具体的业务逻辑。 - dao：数据访问层（Data Access Object）持久层，负责数据访问操作，包括数据的增删改查。 #### 分层解耦 - 耦合：衡量软件中各个层/各个模块的依赖关联程度。 - 内聚：软件中各个功能模块内部的功能联系。 - 软件设计原则：高内聚低耦合 控制反转：Inversion Of Control 简称IOC。对象的创建控制权由程序自身转移到外部（容器），这种思想被称为控制反转。 依赖注入：Dependency Injection简称DI。容器为应用程序提供运行时，所依赖的资源，被称为依赖注入。 Bean对象：IOC容器中创建、管理的对象，称之为Bean。 > 原来通过代码分层，但需要调用各个层之间的功能，我们需要定义一个private成员变量，为了解耦我们需要定义接口多态进行指向，而如果我们想要换个接口实现类，我们需要更改代码，因此耦合度会提升，为了进一步降低耦合度，通过控制反转和依赖注入，利用容器，为代码提供实例对象。 ## IOC&DI详解 #### 入门 1、将Dao及Service层的实现类，交给IOC容器管理。（Invert Of Control） 2、为Controller及Service注入运行时所依赖的对象 （Dependency Injection） @Component注解：我已经将这个类交给了容器 @Autowired 自动找到容器中的bean对象并且赋值给成员变量 ### IOC详解 - 要把某个对象交给IOC容器管理，需要在对应的类上加上如下注解之一： | 注解 | 说明 | 位置 | | ----------- | ------------------ | -------------------------- | | @Component | 声明bean的基础注解 | 不属于以下三类时，用此注解 | | @Controller | Component衍生注解 | 标注在控制层 | | @Service | Component衍生注解 | 标注在业务层 | | @Repository | Component衍生注解 | 标注在数据访问层 | 声明bean的时候，可以通过注解的value属性指定bean的名字，如果没有指定，默认为类名首字母小写。 - 前面声明的bean四大注解，要想生效，还需要被组件扫描注解@ComponentScan扫描 - 该注解虽然没有显示配置，但是实际上已经包含在启动类声明注解@SpringBootApplication中，默认扫描的范围时启动类所在包及其子包。 ### DI详解 - 基于@Autowired进行依赖注入的常见方式有三种 1、属性注入 2、构造函数注入 3、setter注入 等于说就是 一个是通过成员变量自动注入，通过构造器方法注入变量值，通过setter方法注入变量值 构造器注入成员变量需要用final修饰 1、属性注入 - 优点：代码简洁、方便快速开发 - 缺点：隐藏了类之间的依赖关系、可能会破坏类的封装性 2、构造函数注入 - 优点：能清晰地看到类的依赖关系、提高了代码的安全性。 - 缺点：代码繁琐，如果构造函数过多，可能会导致构造函数臃肿 注意：如果只有一个构造函数，@Autowired注解可以省略 3、setter注入 - 优点：保证了类的封装性，依赖关系更清晰。 - 缺点：需要额外编写setter方法，增加了代码量 注意：编写的setter方法需要set类名 - @Autowired注解，默认是按照**类型**进行注入的。 - 如果存在多个相同类型bean，将会报出错误 解决方法： 1、@Primary 2、@Qualifier("注入bean的名字") 类名小写+Autowired 3、@Resource(name="bean的名称")类名小写 bean的名字是类名小写。
